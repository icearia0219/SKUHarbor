## 1. 阶段判断

现阶段适合定位为**带有工程检查记录的电商领域工作台／有边界的工作流 Copilot 初版（PoC）**。材料描述了产品事实、政策、五类任务、质检、审核、导出及持久流程的增量实现，也提供了比静态截图更有价值的测试与模型产物；但本包不能支持“已经生产落地”或“完整验收通过”。

- **A：完整工程与演示验收尚未通过。** 工程检查的通过记录，与内容可用性、独立事实支持、语言质量、真实 PDF 提取等未完成项可以同时存在。
- **B：真实业务试运行未验证。** 缺少按五任务、US/DE分别核对的真实资料、业务人员复核和至少五工作日使用证据。
- **C：经营收益未验证。** 没有可以支持工时节省、销量、转化率、利润或广告收益改善的实验。

这里的验收等级 A/B/C，与模型评测变体 A/B/C 是两套名称。故障变体 C 通过不代表经营收益层 C 完成。`REPORT_TO_WEB_CHATGPT.md` 已明确整体 A 未通过，本审阅认可其分级方式，没有把工程绿灯误写成业务验收。

## 4. 模型成绩要区分“正确补料”和“已有可审核稿”

本次重新统计 `evidence/model-A-report.json` 与 `evidence/model-B-report.json` 的60行结果，得到：

| 统计                      |   A：通用提示 |            B：任务SOP |
| ------------------------- | ------------: | --------------------: |
| 整案通过                  |         25/60 |                 21/60 |
| 通过案中needs_input       |            24 |                    18 |
| 通过案中draft             | 1（广告诊断） | 3（均research_brief） |
| 全部任务中waiting_review  |          1/60 |                  3/60 |
| Listing整案通过           |         10/15 |                  6/15 |

缺证据时正确返回needs_input，属于应当保留的正确行为；不过它与交付可审核的Listing或客服稿是不同成果。**A的Listing 10/15不能表述为生成了10份可用稿。** B的3份待审稿也只属于候选研究任务，不能推广成其他模块已经可用。

两份报告的首次与最终模型schema均为54/54，持久化schema为60/60；这两个分母不同。结构合法不等于事实正确、业务分支正确或草稿已通过质检。不能将“schema 100%”当作“60份内容可用”。报告同时把费用记为unknown、真人语言质量标为not_evaluated，未将缺失证据填成0成本或人工已通过。

材料称两轮真实模型评测使用同一批60个封存案例，第二轮已观察第一轮失败并修复实现。它可以用于冻结材料上的回归比较，不能继续当全新未见测试集证明泛化。B整体低于A，目前没有证据支持“SOP总体改善质量”；更不能据相关小样本宣称统计显著或经营因果。

## 5. 模型失败应分三类调查

当前报告以CLAIM_LOCATION、UNSUPPORTED_CLAIM等代码为主。没有源码与评分实现时，不能判断其中多少是模型错误、定位契约不一致、守卫误报或标签问题；下一步需要在开发集逐例核对原始可见输入、叶子字段、引用和判分原因。

**第一类：输出与校验契约的对齐问题。** 例如 `test-travel-kettle-facts` 两组均出现多个CLAIM_LOCATION，`test-travel-kettle-listing` 的A返回needs_input而B被质检阻断。可复核的是这些状态与代码确实存在；不能直接断言底层使用了哪一种错误字符串/路径算法。应检查模型声明是否定位到真正包含事实的字段，而不是用放宽全部检查来提高分数。

**第二类：可能误报，需要人工判定。** 如 `test-air-fryer-support` 出现SUPPORT_PII或UNSUPPORTED_HANDOFF_EFFECT，`test-garment-steamer-support` 的B又同时触发PII与退款完成守卫。仅凭错误码不能证明文本真的含个人信息，也不能证明守卫错误；应核对句子是在描述用户请求、解释尚未完成，还是在声称系统已经处理。证据包不足以确认正则或语义判定实现。

**第三类：真正的缺料或业务风险。** `test-steam-mop-facts` 的A说明没有可比较候选/有效政策；这可能是正确补料而非需要强行生成。退款完成没有当前回执、规则适用性不明、跨SKU数值无支持等也应继续阻断。应补合法资料或修复具体生成错误，不能为增加draft数量而编认证、承诺到账或把竞品规格赋予本品。

DE检索目前0/0为N/A，7个DE查询缺相关正例分母；US记录的6/6不能替代DE验收。事实支持率、适用必需字段完成率及跨站数值/单位一致性还需要独立计数，不能从整案通过率推导。

## 6. 为什么用户启动后“看不出差异”

`REPORT_TO_WEB_CHATGPT.md` 明确报告：普通聊天仍是原入口，尚未接入电商任务自然语言调度；电商业务在独立路径，手机聊天页缺明显入口，资料导入和首个任务引导也不足。这能合理解释用户的体验反馈：新增领域能力没有在默认使用路径中被发现。

这是**依据包内报告的归因**，本审阅没有打开应用或亲自观察UI。缺截图、路由源码和操作录像时，不能进一步确认具体按钮位置或声称已验证移动端。改进入口与引导可以提升可发现性，但不会自动解决模型质量、资料缺失或业务验收。

## 7. 最需要保留的工程风险与处置边界

1. **真实运行可复现性不足。** 需要与指定commit对应的源码/依赖、冻结输入与评分配置，才能复核实现及报告。当前哈希一致仅覆盖上传导出文件。
2. **Windows权限回归仍有失败。** legacy日志的两个“Private artifact storage is unsafe”及0600/0666差异，可能影响私有成果功能与备份保密。平台差异是合理线索，但缺少目标平台复现与ACL策略验证，不能断言只是无害测试问题；更不能通过删除安全守卫刷绿。
3. **当前模型与最终工程版本不同。** provenance明确A/B针对后续pause/cancel修复前的workflow版本。独立红绿和最终工程检查支持该修复的特定行为，但不能扩展为最终代码已经完整跑过模型验收。
4. **业务内容与用户路径尚未闭环。** Listing、客服均没有待审产物，普通聊天又未接领域任务；应同时跟进内容失败分类和入口/引导，分别验收。
5. **真实数据、语言、运维及费用仍缺证据。** 包内报告还列明真实PDF提取未验证、缺实际价格版本及费用、没有完整生产切换与五工作日试用。它们应留在未验收清单，不由fixture通过替代。

报告提到本机私有Provider临时副本删除曾被自动审批拒绝，并有Windows退出清理遗留。这些凭据文件不应进入证据包；后续由本机按原权限与审批政策检查、撤销或处理，保留必要处置记录，不能绕过拒绝、换工具强删或把秘密复制到公共报告。当前包内的描述不足以确认实际清理已经完成。

## 8. 本次结论的使用方式

可以使用的描述是：已形成电商领域工作台及持久流程初版，有场景检查、部分安全红绿及受控资料模型评测记录；同时明确内容质量未达标，整体A仍未通过，B/C未验证。

下一轮需求与计划应分别覆盖：入口/导入引导、开发集失败分类与契约修复、独立质量指标及新冻结样本、目标环境权限与运维验证。以上方向是审阅建议，本文件没有执行修改，也没有授权平台写入或生产发布。
