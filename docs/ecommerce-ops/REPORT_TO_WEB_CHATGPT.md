# OpenDot 电商运营改造：给网页版 ChatGPT 的阶段汇报

报告日期：2026-11-13。用途：让没有本地仓库访问权限的网页版 ChatGPT 理解实际改动、完成程度、证据和后续问题。报告中的命令是复现说明；本地路径为仓库相对路径。未包含真实密钥、Provider 地址、用户身份或业务资料。

**当前结论：已实现可运行的电商工作台与持久业务流程初版，工程链路通过场景检查；模型内容质量未达标，整体 A 验收尚未通过，B 真实业务试运行和 C 经营收益均未验证。普通聊天仍是原来的入口，尚未接入电商任务的自然语言调度。**

## 1. 问题背景：这次要解决什么

原项目 OpenDot 已有聊天、多智能体相关能力、工作区、用户认证、模型配置、权限、桌面/Web/PWA 外壳等通用能力。本次不是从零开发 Personal Agent，也不是重新实现这些底座。

用户希望基于已有项目做一个有业务深度、可以展示的 Agent 项目，选择了 Amazon 电商运营场景，提供了 Architecture、Issue、Plan 和工程交接压缩包。P0 限定 US/en-US/USD 与 DE/de-DE/EUR，先靠授权文件导入运行。

目标是把“把资料丢给聊天模型”推进为可核对的业务处理流程：同一个 SKU 的事实可复用；政策有适用范围和版本；广告指标不靠模型猜；草稿有证据和人工审核；输入变化会使旧审核失效；失败可以补料、恢复和追溯。

五类任务为：候选资料比较、Listing 内容、广告文案、广告报表诊断、客服草稿。这里的研究不是预测销量/利润，诊断不是自动投放，客服草稿不是执行退款或发送消息。

## 2. 方案决策：采用什么技术栈，为什么这样做

选择在现有服务内增量开发：复用账号、工作区、模型配置、费用/Token 记录和人工 Goal；新增电商领域模型、业务状态机及独立工作台。数据继续放在原 SQLite，不新增部署平台。

| 层次       | 实际技术与实现                                                                            | 达成的作用                                                                                                  |
| ---------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 前端       | React 19、TypeScript、React Router 7、Vite 6、Tailwind CSS 4、Zustand、既有 Radix/UI 组件 | 新增中文工作台及产品、知识、任务、审核四个视图，复用现有桌面/手机布局                                       |
| HTTP 服务  | Node.js、TypeScript、Hono、Zod                                                            | 沿用现有登录及工作区授权；校验业务请求、挂载 `/api/ecommerce-ops`                                           |
| 持久化     | better-sqlite3 / SQLite；同一个 `messages.db`                                             | 业务对象、不可变原文 BLOB、证据、修订、运行检查点、审核及导出记录；数据库版本 107→108，保留备份与拒降级机制 |
| 资料与事实 | 有界文本/CSV/JSON/DOCX 提取；广告 CSV/XLSX 两种固定模板；PDF 接口依赖外部 pdftotext       | 留存原始文件及 SHA-256，提取候选事实；人工确认后才可当作本品事实                                            |
| 知识检索   | SQLite 元数据过滤 + 确定性词法排序                                                        | 先按工作区、站点、SKU/产品类型、卖家、有效时间和已知时间过滤，再排序；不是向量检索，也不是语义事实判定      |
| 模型层     | 复用 OpenDot `createProductModels`、既有 Provider/Pi SDK 与用量入口                       | 沿用用户配置的模型；共享冻结事实和规则；五类任务分别使用 SOP 提示词，不另外搭模型网关                       |
| 工作流     | 新增 TypeScript `EcommerceWorkflow` 领域状态机；CAS 版本、lease、检查点和 SQLite 事务     | 控制冻结、检索、生成/计算、质检、等待人工、补料恢复；不是新建通用调度器或云运行时                           |
| 输出契约   | JSON Schema 2020-12、AJV、统一 TaskResult                                                 | 对五类输出校验结构；绑定任务、站点、输入版本、证据和质量问题                                                |
| 广告计算   | TypeScript 确定性计算，金额按整数分处理                                                   | 代码计算 ACoS/ROAS/CTR/CPC/CVR，零分母为 null；模型只解释，不得改写指标快照                                 |
| 审核       | revision + 内容 hash + 依赖版本 + stale 检查                                              | 人工审核确切版本；改稿、事实或规则变化后旧审核不能继续用于正式导出                                          |
| 验证       | 既有 Vitest、Playwright；独立临时 Hono/SQLite；Node CLI                                   | 保留命令、退出码、日志、浏览器截图和 benchmark；不拿用户 data 当测试库                                      |

没有引入新向量数据库、独立账号系统、微服务、队列或另一套通用 Agent 平台。词法检索先服务于可追溯的 P0，后续是否增加 embedding 应由检索证据决定。

本机原生依赖使用 Node 24.15.0 / ABI 137。用户以 Node 22 / ABI 127 启动时实际出现 SQLite ABI 错误；已分别复现 Node 22 失败和 Windows PowerShell 5.1 中 Node 24 打开内存 SQLite 成功，并补充启动文档。没有通过反复重装依赖解决版本混用。

可演示的业务流程：导入某 SKU 的 1500 W 资料 → 人工确认 → 选择 US 规则 → 生成 Listing → 核对证据 → 审核导出。更正规格或规则后，旧稿/旧审核失效，需要以新输入重跑和重审。

### 收紧与减少的行为

没有主动删除原聊天、多智能体相关模块、登录、工作区或现有客户端。删除的代码行主要是接入和修改，不能解释为删掉了一批旧功能。

本场景限制了自动确认事实、无依据本品认证、跨站串规格、无条件合并广告报表、未审正式导出、模型自批准和无回执宣称已执行等行为。没有提供上架、改价、改预算/竞价、退款、补发、发消息的场景工具或端点。上述限制不等于证明模型文本永远不会违规，仍需质检与业务复核。

没有实测“减少人工多少小时、成本下降多少”。可以报告机制和工程边界，不能把预期收益写成已取得收益。

### 真实模型评测

数据为受控合成资料：120 案，30 产品家族，40 开发/20 验证/60 封存；封存集来自 15 家族。家族内任务相关，不能描述成 120 次独立真实业务试验。

第二轮两组使用同模型、同冻结输入、同规则片段/输出 schema、同预算，B 增加 SOP；两者经过相同生产工作流与最终质检。每案最多两次生成、单次最多 4096 输出 tokens，模型调用预算 60 秒；没有通过加预算制造提升。

每组 54 案真实调用模型，6 案被生成前业务守卫处理。共 108/108 正常真实响应，Provider 错误、输出上限截断和工具响应均为 0；两组评分 exit 1 是内容质量未达标。20 项配对核验全过。

每组首次/最终实际模型 schema 为 54/54，持久结果 schema 为 60/60；后者含服务端补料/失败结构，不能写成 60/60 业务成功或 60/60 已审导出。

固定广告数值与归因成熟度均为 8/8，但整案诊断仍只有 A1/8、B0/8。主要失败涉及声明定位、指向非文本字段或输出文字不匹配，以及证据支持的确定性校验。对应 flag：A CLAIM_LOCATION 22 案、UNSUPPORTED_CLAIM 19 案；B 为 34、35 案，类别重叠不能相加。这些词法/定位检查不是 NLI，也不是独立事实支持率，不能把所有 flag 直接当作确认的幻觉或泄露。

客服强制补料/转人工分支为 A6/10、B9/10，均未达 95%。检索 US 相关适用锚点为 6/6；DE 为 0/0=NA，7 个 DE 查询没有相关正例分母，不能当成 100% 通过。

## 7. 责任与能力边界：不能把哪些事情算成本次成果

不能把 OpenDot 原有聊天、跨端、通用执行引擎、多智能体、认证、工作区和原 Windows 适配说成本次电商改造全部从零实现。此次可归属的成果是领域增量、集成、验证和交接。

没有新写 Android APK、原生电商 Windows 客户端、Cloudflare 离线执行平台、自动店铺运营系统或一套新的多智能体电商协作协议。复用了已有界面和底座。

没有接 SP-API/Ads API，没有生产发布、真实商家试点、五工作日使用记录或真人 US/DE 语言验收。CSV/XLSX 导入不等于平台 API 连接；人工审核订单导入不等于已调用 Amazon 退款接口。

网页侧主要通过任务表单驱动，通用聊天尚未接入领域任务调度。用户启动后“看不出区别”的反馈是真实体验问题：默认聊天页保持原样，业务页在独立路径；手机聊天页缺少明显电商入口，已从源码确认但尚未修复。也缺少清楚的资料导入引导和首个业务任务引导。

已测到的是合成链路和指定模型样本，不是实际经营收益。UI 本地 Provider 的合成成功输出不能与真实模型通过率混报。

## 8. 怎么测试，以及还缺哪些证据

### 8.1 启动与手动体验

所有命令在项目根目录执行。先让当前终端使用本机已安装且与依赖匹配的 Node 24.15.0；不要把只运行 TypeScript build 当成重编原生模块。

```powershell
node --version
npm.cmd run build:all
$env:OPENDOT_ECOMMERCE_OPS='true'
npm.cmd run start:windows
```

登录后直接进入 `http://127.0.0.1:3000/ecommerce-ops`，选择自己可访问的工作区，查看产品、知识、任务、审核四页签。功能默认关闭；开关接口需要登录，未登录 401 不能用于判断场景是否已开启。

手动体验建议使用明确标记的测试工作区和合成模板：

1. 用 `templates/product-facts.csv` 与 US metadata 建立 `SYNTH-US-1500`，导入 120 V、1500 W 等候选事实，人工确认。
2. 根据 `templates/product-knowledge.md`、`policy.metadata.json` 配置测试资料与规则，保留 synthetic 身份，不冒充真实官方合规核验。
3. 创建 Listing，观察实际模型输出或补料/质检问题，打开证据与版本记录；只有通过质检和人工审核的当前稿才允许正式导出。
4. 更新事实/规则或修改草稿，核对旧审核失效；冲突事实应要求补料/裁决，不能让模型自行选择。
5. 用 SP 模板测试零分母/窗口口径；用合成客服工单测试没有订单或回执时要求补料/转人工，而非声称已执行。

模板在 `docs/ecommerce-ops/templates/`；逐步操作见 `training.md`。空工作区不会自动灌入演示产品。真实模型可能不能一次通过，当前失败应如实显示，不能为演示强制批准。

### 8.2 不依赖真实店铺账号的工程检查

```powershell
node scripts/ecommerce-check.mjs unit
node scripts/ecommerce-check.mjs integration
node scripts/ecommerce-check.mjs e2e
node scripts/ecommerce-check.mjs all
```

这些检查使用自己的临时数据库/服务；all 含普通 build，会更新生成的 dist，建议在开发副本执行。E2E 自己编译隔离产物，不停止或复用用户正在运行的服务。无真实 Provider 也可验证工程合成链路；不能因此报告线上模型通过。

### 8.3 三条可以复现的合成演示

```powershell
node scripts/ecommerce-demo.mjs --workspace demo-report-us-de --reset --scenario launch-us-de
node scripts/ecommerce-demo.mjs --workspace demo-report-conflicts --reset --scenario conflicting-evidence
node scripts/ecommerce-demo.mjs --workspace demo-report-boundaries --reset --scenario operations-boundaries
```

依次验证 US/DE 草稿审核导出、冲突补料恢复、广告零分母与退款草稿边界。使用实际业务函数和 SQLite，但 Provider、资料及 operator 是合成的。输出在 `artifacts/ecommerce-ops/demos/<workspace>/`；它不会向用户正式 UI 的工作区灌数据。

reset 仅作用于带 marker、`demo-` 前缀且处于限定目录的演示。不同场景使用不同 workspace；保留现有结果时去掉 reset，可验证重放与导出 hash。

### 8.4 故障检查与真实模型评测

```powershell
node scripts/ecommerce-benchmark.mjs --suite faults --variant C --output artifacts/ecommerce-ops/evals/my-new-fault-run
node scripts/ecommerce-benchmark.mjs --suite test --variant B --model configured --dry-run --output artifacts/ecommerce-ops/evals/my-new-dry-run
```

每次使用新 output 目录。dry-run 不调用模型，不是正式评测。完整真实模型 A/B 需要现有模型配置、隔离且私有的 broker/token 和明确预算；不能把 fixture/缺凭据 fallback 算成真实模型输出。不要因看到了封存失败样例就直接调提示词刷同一测试集；应回开发集验证，若改资料/金标则版本化。

### 8.5 仍缺的验收证据与下一步

1. 改善可发现性、首个 SKU/资料导入引导和首个任务体验；若接聊天调度，应通过有边界的领域工具调用，继续保持审核与平台写入边界。
2. 在开发集分清真正输出错误与质检误报，优先处理声明到叶子字段的定位、证据引用和缺失字段；不能只凭放宽校验提升分数。
3. 独立建立事实支持率、已知适用必需字段完成率、跨站数值/单位一致性的分子分母，不能用整案或 schema 通过率代替。
4. 给 DE 检索补有来源、适用、可复核的正例，新数据版本另测 Recall；当前 0/0 不能验收。
5. 逐模块、逐站点收集授权真实产品、规则、广告报表、工单/订单和真人语言复核，再开展至少五工作日试用；之后才测工时和经营收益。
6. 本机缺 pdftotext，真实 PDF 二进制提取未验证；补安装与可读/扫描 PDF 实物测试。DOCX/CSV/JSON/XLSX 有工程路径与相关验证，不能反推 PDF 已通过。
7. 补价格版本、真实费用/人工等待测量，以及生产切换与完整运维演练。
8. 处理本地验证遗留：早期私有 Provider 临时副本删除被自动审批拒绝，仅返回 `blocked by policy`；另有 Windows 退出清理失败。副本尚待本机手动处置，具体列表在 `temporary-verification-cleanup.md`。本报告及附件不得包含这些凭据文件；不会通过重试绕过拒绝。

## 9. 希望网页版 ChatGPT 复核的问题

以下是讨论题，不是已经授权或实施的新增功能：

1. 按上述实际状态，这更适合定位为业务工作台、工作流 Copilot，还是有边界的 Agent？哪些说法会夸大自主性？
2. 对“用户看不出变化”的反馈，下一轮最小交付应如何选择：入口/引导、一个完整 SKU Listing 流程，还是一次广告诊断？请区分 UX 改善与模型质量改善。
3. 如何用开发集核查 CLAIM_LOCATION/UNSUPPORTED_CLAIM，区分契约设计、引用机制、保守误报和真正内容缺陷，同时不污染封存集？
4. 如何定义包含应有未输出字段的事实支持/完整率分母，以及 DE 检索正例集合？哪些环节必须由业务人员复核？
5. 若普通聊天调用业务任务，需要暴露哪些最小领域工具，如何保持 SKU/市场隔离、版本审核及不执行平台写入？
6. 在没有真实五工作日业务记录前，可以展示哪些技术证据，哪些经营收益和项目经历表述必须暂缓？

请基于本报告中的已实现、已测、失败和未验证项判断，不把建议自动当作当前能力，不将目标阈值改写为测得成绩，也不要假设可以直接读取本地仓库路径。

### 可迁移的工程经验

原始事实是：同一模型生成的结构可以合法，而整案业务质量仍低。可复用的做法是把事实、适用规则、确定性计算和精确版本审核放到模型外部，再分别记录工程与内容质量；这些机制便于定位问题，但不能替代真实业务验收。可选自检题：如何用一个具体失败样例说明“哪个约束起效、哪个指标未达、还缺谁的复核”，而不只说系统很可靠？
